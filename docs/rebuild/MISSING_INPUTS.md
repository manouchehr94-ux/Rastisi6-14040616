# MISSING_INPUTS — ورودی‌هایی که در GitHub نبودند

> هیچ محصول، تصویر، قالب یا تنظیمی برای دو فروشگاه از خودم ساخته نشده است. هر ردیف زیر یا «در Git موجود و صحت‌سنجی‌شده» است یا **MISSING SOURCE**.

## ۱. خلاصه

| وضعیت | معنی |
|---|---|
| **MISSING SOURCE** | داده‌ی اصلی دو دمو در Git/محیط ابری نیست؛ باید از بیرون تحویل شود |
| ابزار آماده | importer + validator + exporter + integrity checker نوشته و با داده‌ی *تست‌ساز* و داده‌ی seed مخزن آزمایش شده‌اند (نه با داده‌ی واقعی دمو) |

## ۲ب. به‌روزرسانی: قالب ورودی مشخص شد و ابزار تبدیل آماده است

مالک پروژه اعلام کرد منابع اصلی چهار فایل‌اند: `demo_v5.sqlite3` + `demo_v5_media.zip` و `demo_arch02.sqlite3` + `demo_arch02_media.zip` — **دو دیتابیس SQLite مستقل** (کلیدهای اصلی هم‌پوشان). این فایل‌ها هنوز در GitHub یا این محیط **نیستند** و اجرا نشده‌اند، پس وضعیت داده همچنان **BLOCKED** است. ابزار `build_demo_bundle` (راهنما: [`OFFLINE_WINDOWS_GUIDE.md`](OFFLINE_WINDOWS_GUIDE.md)) دقیقاً همین ورودی را می‌پذیرد، شناسه‌ها را ایمن بازنگاشت می‌کند و فقط پس از اعتبارسنجی کامل bundle می‌سازد.

## ۳. چگونه تحویل داده شود (روش امن، بدون Git)

> مسیر اصلی اکنون: اجرای `build_demo_bundle` روی لپ‌تاپ روی همان چهار فایل (بخش ۲ب). مسیر زیر (`export_store_bundle`) فقط وقتی لازم است که هر دو فروشگاه در **یک** دیتابیس باشند.

1. روی ماشینی که هنوز داده‌ی اصلی را دارد، با همین کد (همین شاخه) اجرا شود:
   ```bash
   python manage.py export_store_bundle \
       --store <slug-قبلی-دمو۱>=demo_v5 --store <slug-قبلی-دمو۲>=demo_arch02 \
       --out /secure/path/bundle --media-root /path/to/old/media
   ```
   (باید هر دو فروشگاه از **یک** دیتابیس منبع صادر شوند تا کلیدهای اصلی با هم تداخل نکنند — بخش «محدودیت کلید اصلی» در [`DATA_MAPPING.md`](DATA_MAPPING.md).)
2. خروجی (`manifest.json`, `stores/`, `media/`) روی VPS یا محیط ساخت، **خارج از Git**، کپی شود (`scp`/`rsync`).
3. `python manage.py validate_demo_bundle /path/to/bundle` باید `PASS` بدهد؛ در غیر این‌صورت گزارش دقیق می‌گوید چه چیزی کم/خراب است.
4. اگر دیتابیس قدیمی با نسخه‌ی کد متفاوتی ساخته شده، ابتدا همان نسخه‌ی کد را بالا بیاورید و export را از آن بگیرید (فرمت bundle مستقل از نسخه‌ی کد است ولی schema مدل‌ها باید با این شاخه سازگار باشد).

اگر فقط فایل خام SQLite/dump در دست است: یک دیتابیس موقت با کد قدیمی بسازید، `migrate` + بازیابی کنید و مرحله‌ی ۱ را روی آن اجرا کنید.

## ۴. نکته‌ی مهم درباره‌ی seed موجود در مخزن (سرنخ، نه جایگزین)

مخزن یک فروشگاه نمایشی واقعی با دارایی‌های صحت‌سنجی‌شده دارد (`rasti-mode-demo`، ۵۰ محصول، **۱۵۰ تصویر**، ۴۱ تصویر curated). تعداد «۵۰ محصول / ۱۵۰ تصویر» با گزارش قبلیِ دموی V5 هم‌خوان است، ولی:

- این **اثبات** نمی‌کند که `demo_v5` از همین seed ساخته شده؛ طرح/نسخه‌های Studio، ShopSettings و رنگ/لوگوی آن دموها از مخزن قابل استخراج نیست؛
- بنابراین از آن به‌عنوان «داده‌ی اصلی دمو» استفاده یا ادعا نشد. می‌توان آن را جداگانه با `seed_ready_template_fashion_demo --ready-template <key>` در محیط آزمایشی ساخت، اما فروشگاه حاصل `rasti-mode-demo` است، نه `demo-v5`.

## ۵. آنچه بدون این ورودی‌ها وضعیت‌دار `BLOCKED` می‌ماند

- تطابق بصری با دموهای اصلی (CSS/JS/هدر/فوتر/لوگو/فونت/بنر)
- شمارش نهایی ۱۰۰ محصول / ۳۰۱ رکورد تصویر / ۱۲۶ صفحه / ۳۳۵ فایل رسانه
- رندر نسخه‌ی منتشرشده و پیش‌نویس‌های واقعیِ هر دمو
- هر ادعای `READY FOR DEPLOYMENT`

وضعیت کلی: **`CODE READY / DATA BLOCKED`**.
