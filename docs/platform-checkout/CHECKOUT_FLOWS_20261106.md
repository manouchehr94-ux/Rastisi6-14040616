شاخه‌ی محلی `dev/platform-checkout-unify-20261106` (از مبنای `d08dbe91`). **هیچ موتورِ پرداختِ دومی ساخته نشد**: تسویه فقط ترکیبِ خواندنیِ
`platform_gateway_service` (آمادگیِ روش‌ها) + رکوردهایِ سرور (فاکتور/خرید/تلاش/ادعا) است؛ جابه‌جاییِ پول همان `payment_flow_service`،
`sms_purchase_payment_service` و `manual_card_service` است.

## ۲. مسیرهایِ تسویه (سمتِ مرچنت؛ میزبانِ مدیریتِ همان Store؛ بدونِ سایدبارِ مدیرِ پلتفرم)

| مسیر | کار |
|---|---|
| `GET /admin-portal/billing/checkout/<subscription\|sms>/<id>/` | صفحه‌ی تسویه (خلاصه، روش‌هایِ آماده، وضعیت) |
| `POST …/pay/` (`method`, `ack`) | شروعِ پرداخت؛ فقط یکی از روش‌هایِ **آمادهٔ همین خرید** |
| `POST …/status/` | «بررسیِ وضعیت»: همان verify سرور-به-سرور (محدودِ نرخ، idempotent) |
| `…/billing/invoices/<id>/card-to-card/`، `…/settings/sms/package/purchase/<id>/card-to-card/` | فرمِ ادعا؛ پس از ثبت/لغو به تسویه برمی‌گردد |
| `GET /billing/return/<token>/` (میزبانِ پلتفرم) | بازگشتِ بانک؛ verify سرور ⇒ ریدایرکت به همان صفحه‌ی تسویه |
| سازگاری | `billing-pay`، `settings-sms-purchase-pay`، `billing-card-handoff` ⇒ همان مسیرِ تسویه |

### نمودارِ جریانِ اشتراک
```
مرچنت ─ پرتال «پلن‌ها» (rastisi.<dom>/app/stores/<id>/billing/) ──[خرید]──▶ billing_checkout (POST)
   │  (احرازِ SUBSCRIPTION_CHANGE+BILLING_PAYMENT_MANAGE، Step-Up اختیاری، دورهٔ انتخابی اعتبارسنجی)
   │  اگر هیچ روشِ آماده نیست ⇒ پیام + هیچ فاکتوری ساخته نمی‌شود
   ▼
plan_change_billing_service.start_plan_change → فاکتورِ PLAN_CHANGE (مبلغِ سرور؛ دوره حفظ می‌شود)
   ▼  handoff امنِ cross-host (ticket کوتاه‌عمر)
admin-host: /admin-portal/billing/checkout/subscription/<invoice>/   ◀── داشبورد: پیش‌نمایش→اجرایِ تغییر پلن، فاکتور، نمایِ صورتحساب
   ├─ روشِ آنلاین ─▶ payment_flow_service.start_payment (تلاشِ سرور، return_to=همین صفحه) ─▶ بانک
   │                   ─▶ /billing/return/<token>/ ─▶ verify سرور-به-سرور ─▶ confirm_payment (قفل/idempotent) ─▶ فعال‌سازی/تمدید
   └─ کارت‌به‌کارت ─▶ فرمِ ادعا ─▶ PENDING_REVIEW (صفحه‌ی «در انتظارِ بررسی») ─▶ مدیرِ مالی (بدونِ خودتأییدی) ─▶ confirm_payment
```
### نمودارِ جریانِ بسته‌ی پیامک
```
تنظیماتِ پیامک ──[خرید و پرداخت]──▶ settings_sms_package_purchase (POST)
   │  هیچ روشِ آماده ⇒ پیام، هیچ خریدِ pending ساخته نمی‌شود (دکمه هم غیرفعال است)
   ▼
SmsPackagePurchase(PENDING، قیمتِ اسنپ‌شاتِ سرور؛ خریدِ pendingِ همان بسته دوباره استفاده می‌شود)
   ▼
/admin-portal/billing/checkout/sms/<purchase>/   (همان صفحه، همان روش‌ها، قوانینِ تسویه‌ی SMS)
   ├─ آنلاین ─▶ sms_purchase_payment_service.start_payment ─▶ بانک ─▶ verify_and_fulfill ─▶ balance_service.complete_purchase (دفترِ تغییرناپذیر، دقیقاً یک‌بار)
   └─ کارت‌به‌کارت ─▶ ادعا ─▶ PENDING_REVIEW ─▶ تأییدِ مالی ─▶ اعتبار (همان دفتر)
```

## ۳. وضعیت‌هایِ تسویه (`platform_checkout_service.state` — فقط از رکوردهایِ سرور)

| وضعیت | شرط | پرداختِ دوباره؟ |
|---|---|---|
| `payable` | فاکتور/خریدِ قابلِ پرداخت و بدونِ تلاش/ادعا | بله |
| `verifying` | تلاشِ آنلاینِ pending (≤ ۴۵ دقیقه) | فقط با «پرداختِ قبلی را کامل نکرده‌ام» (`ack`) + دکمه‌ی «بررسیِ وضعیت» |
| `pending_review` | ادعای کارت‌به‌کارتِ در انتظار | خیر (یک ادعایِ فعال برای هر هدف) |
| `needs_action` | REQUIRES_ACTION / مبلغِ ناهمخوان / تأییدِ بدونِ اعمال | خیر (پشتیبانی/تطبیق) |
| `failed` | ناموفق/لغو/منقضی/ردِ ادعا (با دلیل) | بله |
| `paid` / `refunded` / `closed` | وضعیتِ نهاییِ فاکتور/خرید | خیر |

## ۴. ماتریسِ آمادگیِ روش‌ها (سمتِ تسویه؛ همان ماتریسِ PR #40)

| روش | در تسویه دیده می‌شود وقتی… | در این QA |
|---|---|---|
| زیبال / زرین‌پال / پاسارگاد | فعال + اعتبارنامه‌ی کامل + دامنه‌ی بازگشتِ canonical معتبر + نوعِ خریدِ مجاز | زیبال با پاسخِ شبیه‌سازی‌شده |
| سامان (SEP)، **ملت (Behpardakht)** | بالا + **هر دو گیت** `contract_verification` و `live_verification` توسطِ مدیرِ پلتفرم با ارجاع | ملت با اعتبارنامه‌ی ساختگی: بدونِ گیت **هرگز** نمایش داده نمی‌شود؛ با هر دو گیت برای هر دو محصول نمایش داده می‌شود؛ ابطالِ یک گیت آن را پس می‌گیرد (تست‌ها) |
| اسنپ‌پی / ترب‌پی | `provider_approval` + `live_verification` | پنهان |
| پارسیان، سداد، تجارت | هرگز (پیاده نشده) | پنهان؛ POST دستی رد می‌شود |
| کارت‌به‌کارتِ پلتفرم | فعال + کارتِ مقصدِ معتبر + نوعِ خریدِ مجاز | نمایش با حسابِ پلتفرم |

## ۵. نتایجِ آزمون

**PostgreSQL ۱۶** (`apps.billing.tests.test_platform_checkout`: 41 تست؛ همه‌ی ماتریسِ پذیرش برایِ **هر دو محصول**):
روشِ آماده/ناآماده (غیرفعال، ناقص، gated، پیاده‌نشده)؛ ملت؛ مبلغِ دستکاری‌شده؛ بازگشتِ بانک ≠ مدرک؛ پرداختِ موفق (یک‌بار)؛ ردشده/لغو؛ مهلتِ
گذشته + پرداختِ دیرهنگام؛ callbackِ تکراری؛ ناهمخوانیِ مبلغ؛ cross-tenant (404)؛ نقشِ بدونِ مجوز (403)؛ ارتقایِ پلن با حفظِ دورهٔ سالانه؛ خطایِ
درگاه؛ شکستِ اعمال و بازیابیِ امن؛ کارت‌به‌کارت: pending/تأیید/تأییدِ تکراری/ردِ با دلیل/لغو/انقضا/خودتأییدی/مبلغِ غلط؛ همزمانیِ
۴ نخی برایِ هر دو محصول (`TransactionTestCase`، قفلِ ردیف). تست‌هایِ قدیمیِ ۱۶ فایل به مسیرِ واقعیِ جدید مهاجرت یافتند (بدونِ حذفِ پوشش).

**رگرسیونِ کامل PostgreSQL** (`apps.billing apps.portal apps.sms apps.subscriptions apps.dashboard apps.notifications`): ۴۷۰۶ تست. پس از رفعِ دو ناسازگاریِ واقعیِ کشف‌شده (نقشه‌ی ناوبریِ داشبورد برایِ مسیرهایِ جدید؛ تست‌هایِ ارتقایِ پلن که روشِ آماده نداشتند) فقط **۷ خطایِ از قبل موجود** می‌ماند که روی commit مبنا (`d08dbe91`) نیز **عیناً** رخ می‌دهد (`LegacyRetainedExportTests` ×۵ و دو تستِ `product_options…` — وابسته به PostgreSQL، نامرتبط با پرداخت). `makemigrations --check`: بدونِ تغییر.

**مرورگر (Chromium، دیتابیسِ یک‌بارمصرف، درگاهِ شبیه‌ساز)**: ۱۴۲/۱۴۲ بررسی، ۰ خطایِ کنسول؛ ژورنال‌هایِ A (اشتراک آنلاین)، B (SMS آنلاین با لغو → تلاشِ
دوباره → موفق)، C (اشتراک کارت‌به‌کارت → در انتظار → تأییدِ مالی)، D (SMS کارت‌به‌کارت → ردِ با دلیل)، E (بدونِ روشِ آماده)؛ ۱۴۴۰/۷۶۸/۳۹۰،
RTL، بدونِ سرریزِ افقی، ارقامِ فارسی، بدونِ سایدبارِ مدیرِ پلتفرم، بدونِ رازِ اعتبارنامه در HTML.

## ۶. محدودیت‌هایِ بیرونیِ باقی‌مانده (صادقانه)

* **ملت (Behpardakht)**: آداپتر و تست‌هایِ قراردادی با پاسخِ شبیه‌سازی وجود دارد؛ **هیچ تراکنشِ واقعی انجام نشده**. مانع‌ها: پایانه/نام‌کاربری/گذرواژه‌ی
  خودِ راستیسی از بانک ملت؛ ثبتِ IP و دامنه‌ی بازگشت؛ گواهیِ مدیر برایِ هر دو گیت. تا آن زمان هرگز در تسویه نمی‌آید.
* هیچ درگاهِ واقعی در این QA تماس نگرفت؛ رفتارِ واقعیِ زیبال/زرین‌پال/پاسارگاد فقط با sandbox/تراکنشِ حداقلیِ مدیر قابلِ تأیید است.
* ورودِ مرچنت از پرتال به تسویه نیازمندِ دسترسی به میزبانِ مدیریتِ همان Store است (Store باید `ACTIVE` باشد؛ فروشگاهِ معلق به پنل نمی‌رسد).
* **اثرِ رفتاری**: دیگر هیچ «تلاشِ manual-provider» یا خریدِ SMSِ بی‌راه ساخته نمی‌شود؛ تأییدِ دستیِ ادمین برایِ خریدِ pending (`/payments/sms-purchases/`)
  برایِ مواردِ موجود دست‌نخورده می‌ماند.
* زنگِ اعلان گاهی در لحظه‌ی ناوبریِ سریع «دریافتِ اعلان‌ها ممکن نشد» می‌گوید (fetchِ لغوشده)؛ نامرتبط با این تغییر و بررسی نشد.
