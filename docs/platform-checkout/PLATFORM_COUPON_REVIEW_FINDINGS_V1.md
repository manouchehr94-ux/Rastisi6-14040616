# Platform coupons: review findings and decisions (v1)

Response to the 2026-11-08 review (verdict NEEDS_CHANGES).

| # | Finding | Decision | Where |
|---|---------|----------|-------|
| 1 | Reservation not held across manual card claims | **Fixed.** `submit_claim` calls `hold_reservation_for_claim`: the reservation is re-validated/renewed (`reservation_lost` becomes a `ClaimError` and no claim is created) and pinned to the claim review window (`REVIEW_WINDOW_DAYS`, 7). When the claim is rejected, cancelled or expires, `restore_reservation_lifetime` returns it to the normal 30-minute lifetime. | `manual_card_service`, `platform_coupon_service` |
| 2 | Over-redemption after lapse | **Policy kept, now explicit and audited.** Money already received is never refused: the recorded discount is honoured. If other counted redemptions already fill `max_redemptions` / `max_per_store` at redemption time, a `over_redeemed` coupon audit event (scope `total` or `store`, `from` = prior status) and a `billing.platform_coupon_over_redeemed` audit log entry are written for finance follow-up. The gateway path is also shortened in practice because claims now pin the reservation. | `redeem_for_paid_invoice` |
| 3 | Probing / no throttle | **Fixed with throttling, messages unchanged.** The owner requires distinct Persian messages for invalid, expired, inactive and limit-reached codes, so uniform messages were not adopted. Apply, plan preview and plan execute are limited per user+store (`PLATFORM_COUPON_ATTEMPTS_PER_MINUTE`, default 10, project `rate_limit` cache; fail-closed). Private coupons still answer exactly like unknown codes. | `check_attempt_rate` |
| 4 | Sweeper unwired | **Fixed.** `manage.py release_expired_platform_coupon_reservations [--dry-run]`; schedule every 5-15 minutes. Counting never depends on it. | `apps/billing/management/commands` |
| 5 | Plan-change coupon applied after invoice creation | **Re-evaluated and changed: now atomic.** Invoice creation (`start_plan_change`) and `apply_coupon_to_invoice` run in one `transaction.atomic()`. If applying fails for a *newly created* invoice (race after pre-validation), everything rolls back (no undiscounted invoice, no stray redemption, any superseded scheduled change is restored) and the user is told no invoice was created. If the invoice pre-existed (idempotent reuse) it is left untouched and the user is told (for example `incompatible` with a different manual coupon). | `subscription_plan_execute` |
| 6 | Appendix A parity | **Verified.** The owner's Appendix A is stored at `docs/legal/PRIVACY_POLICY_APPENDIX_A.md` and `apps/portal/tests/test_privacy_policy_exact_text.py` compares the rendered `/privacy/` article block by block (ZWNJ-sensitive; only whitespace and markdown markers normalized), the H1 and the contact link (`/contact/`). Terms section 18 and the "پیش‌نویس" eyebrow are unchanged (owner named only the one notice paragraph); confirm with the owner. | `_privacy_body.html`, `public/terms.html` |

Not covered by automated tests: true concurrent last-slot contention (needs PostgreSQL row locks; SQLite ignores them).

## Added in v2: first paid purchase after Trial

The first paid purchase of a trial store is a `plan_change` invoice (`portal.views._start_purchase`: the first purchase is an upgrade from the free trial plan), so the default coupon (`allow_initial=True`, `allow_plan_change=False`) used to be rejected there. `platform_coupon_service.purpose_for()` now maps a `plan_change` invoice to the `initial` purpose when the subscription is pending/trialing (or ever had a trial) and the store has no real paid invoice. Ordinary upgrades by paying customers stay `plan_change`. A coupon limited to `allow_plan_change` does not apply to the first purchase (decision to confirm with the owner). Tests: `CouponFirstPaidPurchaseAfterTrialTests`.

Finding 2 re-evaluation: honouring money already received and auditing the overage is kept (refusing a settled payment would be worse); a reservation is also pinned during manual claims, which is the long path. A webhook arriving after a 30-minute gateway reservation lapse can still over-redeem by one and is audited (`over_redeemed`).
