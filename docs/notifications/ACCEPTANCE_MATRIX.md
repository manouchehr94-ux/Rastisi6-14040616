# Functional acceptance matrix (scenarios A–N)

Generated by the real-HTTP walk-through `tools/windows-qa/qa_http_acceptance.py` against a running QA server + worker
(host-based routing, cookies, CSRF, central-login handoff; **fake** e-mail provider — no network). Last full run on commit
`eb7834ad` under PowerShell 7.4.6 on Linux: **55 automated checks passed, 0 failed, 3 manual-only**. The machine-readable
report is written to each run folder as `ACCEPTANCE-REPORT.md` / `acceptance.json`.

> "AUTOMATED ✅" = asserted by the walk-through and passing. "MANUAL" = needs a human (a real browser, your eyes, or real time)
> and is **not** claimed as passed here. Nothing below proves real deliverability — the provider is the in-process fake.

## The 3 manual items, restated for the product owner
1. **L** — buy a product on the demo storefront with cash-on-delivery and confirm the order + confirmation page render and the order mail appears in the fake mailbox.
2. **M** — look at the sender, channels, template, history and platform pages at a desktop width and a phone width; confirm RTL, no horizontal scroll (except inside the DNS table), buttons reachable.
3. **N (real time)** — optional: leave a notification past its TTL and confirm it is marked expired, never sent late. The engine logic is unit-tested; a wall-clock reproduction is a judgement call for the owner.

## How to reproduce
On the running QA server (see `tools/windows-qa/README-WINDOWS-QA.md`):
`powershell -ExecutionPolicy Bypass -File .\tools\windows-qa\Invoke-RastiSiAcceptanceCheck.ps1`
(`-Only A,K` to run a subset). It prints each check and writes `ACCEPTANCE-REPORT.md` into the run folder.
