# راهنمای کوتاه انتشار نسخه (برای مالک)

> این سند خلاصهٔ فارسی `RELEASE_PIPELINE.md` است. تا زمانی که مالک مراحل «راه‌اندازی اولیه» را تأیید و اجرا نکند، **هیچ‌کدام از این‌ها روی سرور واقعی فعال نیست.**

## ایده در یک جمله
هر نسخه یک پوشهٔ جدا و تغییرناپذیر است. سایت با یک «اشاره‌گر» (`current`) به نسخهٔ فعال وصل است. نسخهٔ جدید کنار نسخهٔ قبلی ساخته و بررسی می‌شود، بعد اشاره‌گر عوض می‌شود. دیتابیس، تصاویر و رمزها **بیرون** از نسخه‌اند و با انتشار یا بازگشت هرگز دست نمی‌خورند.

## انتشار یک اصلاح (روزمره)
1. برنامه‌نویس اصلاح را در یک شاخه می‌سازد و Pull Request می‌زند؛ تست‌ها خودکار اجرا می‌شوند.
2. بعد از بازبینی، اصلاح وارد شاخهٔ انتشار می‌شود.
3. در GitHub: **Actions ← Release to production ← Run workflow**
   * `sha`: شناسهٔ کامل ۴۰ حرفی کامیت جدید
   * `from_sha`: کامیتی که **همین الان** روی سرور اجرا می‌شود (در خروجی `status` یا خلاصهٔ آخرین انتشار دیده می‌شود)
   * اگر گزارش مایگریشن «REVIEW» یا «DESTRUCTIVE» بود، قبل از تأیید آن را بخوانید.
4. در خلاصهٔ اجرا «Deployment plan» را بخوانید (چه تغییر می‌کند، مایگریشن چیست، بازگشت خودکار ممکن است یا نه).
5. در صفحهٔ اجرا **Review deployments ← production ← Approve**.
6. منتظر `RESULT: OK` بمانید و یک صفحه (ورود) را با دست امتحان کنید.

## معنی نتیجه‌ها
| نتیجه | یعنی | کار شما |
|---|---|---|
| `RESULT: OK` | منتشر و بررسی شد | هیچ |
| `ROLLED BACK` (۱) | نسخهٔ جدید سالم نبود؛ خودکار به نسخهٔ قبل برگشت | خطا را در لاگ بخوانید، اصلاح و دوباره منتشر کنید |
| `NEEDS A HUMAN` (۲) | سیستم ایمن بودن بازگشت را ثابت نکرد و **متوقف شد** | دوباره اجرا نکنید؛ بخش «ایراد» را ببینید |
| `MIGRATION FAILED` (۳) | مایگریشن شکست خورد؛ نسخهٔ قبل هنوز فعال است | اصلاح و دوباره منتشر کنید |
| `REFUSED BY POLICY` (۴) | شرطی (بکاپ تازه، تأیید مایگریشن، وضعیت محیط) برقرار نبود؛ چیزی عوض نشد | پیام را بخوانید |
| `BUSY` (۷۵) | انتشار دیگری در حال اجراست | صبر کنید |

## بازگشت به نسخهٔ قبل
**Actions ← Roll back production ← Run workflow** (`to = previous`) و تأیید. فقط کد برمی‌گردد؛ سفارش‌ها و اطلاعات ثبت‌شده در این فاصله می‌مانند. اگر نسخهٔ آخر مایگریشن غیرافزایشی داشته باشد، سیستم بدون عبارت تأیید ویژه اجازه نمی‌دهد.

## ایراد: «NEEDS A HUMAN»
روی سرور: وضعیت را ببینید (`status`) و فایل `state/INCIDENT` را بخوانید؛ سایت و دیتابیس را با دست بررسی کنید؛ تصمیم بگیرید (بازگشت یا اصلاح)؛ سپس `resolve --note "چه چیزی بررسی شد"`. تا آن موقع هر انتشار جدید رد می‌شود (این عمدی است).

## بکاپ
شبانه، رمزگذاری‌شده، **بیرون از سرور**، با بررسی خودکار صحت و آزمون بازیابی ماهانه. جزئیات و روش بازیابی در `BACKUP_AND_RECOVERY.md`. **رمز مخزن بکاپ را در مدیر رمز نگه دارید؛ بدون آن بکاپ‌ها بی‌فایده‌اند.**

## کارهایی که فقط مالک می‌تواند انجام دهد
۱) تعیین شاخهٔ انتشار (پیشنهاد: `release/production` روی کامیت فعلی)؛ ۲) ساخت Environment به نام `production` با تأییدکنندهٔ اجباری؛ ۳) ساخت کلید SSH و گذاشتن نیمهٔ خصوصی در GitHub و نیمهٔ عمومی روی سرور؛ ۴) مقصد بکاپ بیرونی؛ ۵) نصب ابزار روی سرور و یک‌بار فعال‌سازی. فهرست دقیق: `RELEASE_PIPELINE.md` بخش‌های ۸ و ۱۰.
